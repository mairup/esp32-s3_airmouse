# Toit and Microcontroller Programming in Its Ecosystem

## Foreword

For the VIN course project, I decided to use the Toit programming language because I wanted to try out a new technology, as microcontrollers are still predominantly programmed in lower-level languages like C.

Toit made a very appealing first impression on me, as it was created by engineers from Google who also contributed to Dart, with which I already have some experience and find enjoyable to use. I noticed many similarities in Toit, which made me all the more eager to try it out.

## Briefly About Toit and the Jaguar Tool

Toit is a modern, high-level, object-oriented programming language. Before execution, it is compiled into machine code. It exclusively supports Espressif devices, namely microcontrollers from the ESP32 family. Our project utilized the ESP32-S3 SoC.

The Toit virtual machine runs directly on the microcontroller. Under the hood, this VM uses FreeRTOS, on top of which it implements all language features such as thread scheduling, memory management, and I/O handling.  
I would like to add here that thread scheduling operates on a cooperative round-robin scheduler. The fundamental unit for a thread (which our VM schedules) is called a Task in Toit. Creating tasks is similar to creating objects, and their resources are similarly managed by the garbage collector.

As a developer, you work at the container level running on the VM on the microcontroller. Each program is deployed on the microcontroller inside its own container and has a completely isolated address space. Programs communicate with each other exclusively through inter-process interfaces provided and managed by the Toit virtual machine.

For this project, given the scope of the problem, we decided to use only a single application container. Thus, only two containers run on the microcontroller: our application and Jaguar.

As the only other program running on our microcontroller in the project, Jaguar deserves a few words of its own.

Jaguar is a tool that provides a command-line interface with which we can manage containers on our microcontroller wirelessly over Wi-Fi.

In my experience, updating our program (which has a monolithic design) took approximately 5 seconds on average, and up to 10 seconds under harsher conditions.

## Thoughts After Using the Language in the Project

I am happy to report that Toit was quite pleasant to use. As an object-oriented language, it is inherently very similar to many other popular languages. I like that it nicely incorporates and natively supports declarative programming patterns that blend seamlessly with the language's object structure.

I would also say that language models were more proficient at generating code for Toit than they would have been for lower-level languages. While I don't have concrete comparative data against other languages, as a programmer I found it easier and quicker to understand code generated by agents, while they had an easier time thanks to Toit's relative proximity to natural language.

Iterations across various functional prototypes of our project were fast and straightforward. Issues arose when we began utilizing the Wi-Fi antenna ourselves, but everything was quickly resolved and was more of a developer error.

Regarding performance, I also do not have exact benchmarks. For our use case, it was plenty fast, and that was all I needed. The code itself is compiled to machine code, so it shouldn't be overly slow despite high-level abstractions and automatic memory management. Some sources report that it is "much faster than MicroPython," though I do not have direct personal experience comparing the two.

## Conclusion

Using the Toit language and its development environment proved to be a success. Throughout project development, I frequently noticed how much the chosen ecosystem helped solve problems that would likely have been considerably more demanding in other environments. The end result is (in my opinion) an exciting project developed in a relatively short timeframe by a small team of developers.
